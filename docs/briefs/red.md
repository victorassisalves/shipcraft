# RED brief (acceptance author)

The coordinator includes this brief when assigning a spec item's acceptance cases. An internal trial found that 6 of 11 blockers were clear rules without a discriminating case.

**Author:** Codex (GPT-6.1-Sol, low effort), in a separate session. In a measured comparison, low effort covered 41 of 42 cases, caught the flow-YAML defect that escaped another model, and cost 3 minutes and 69k tokens. Medium and high added no coverage. Revisit the choice if another misreading escapes.

1. **Read only the item's spec and the existing battery.** Do not read the implementation.
2. **Write two cases for each rule:** the ordinary example and a boundary that a rushed GREEN could get wrong while passing the example. Examples: a hardcoded filename, almost-correct output, the wrong config, or running everything before filtering. Prefer a few discriminating cases over many similar ones.
3. **RED check:** run against the current binary. Every new case must fail for the right reason. Report cases that already pass: either identify existing behavior or strengthen a case that does not discriminate.
4. **Ambiguities:** list each one and your reading in one line. The coordinator resolves it in the spec before GREEN.
4b. **Failure paths of what the item records or refuses.** For each row, file, status or refusal the item produces, add a case where a later step of the same command fails: a publish or network call, invalid config, or a write error. The case checks that the record still says what the spec requires. In item 38, both review findings were such paths, and the second review round cost 26 minutes.
5. **Budget:** put cases in `acceptance/lib/item<N>.sh` and fixed points in `acceptance/pontos/<item>.md`, one per line. The runner discovers them. Do not add item-specific lines to `run.sh`, `lib/v1.sh` or the README: shared-file edits caused five conflicts in one evening. Keep the report to one page: counts, already-passing cases and ambiguities.
6. **Refusals use three lines:** what happened, why, next step. Refusal codes (`foreign-hook`, `case-broke`, etc.) are log fields, not terminal text. Check them only in `.git/shipcraft/runs.jsonl` for measured layers (hook, CI, review). `init` does not append there; a refused init preserves `.git/shipcraft`.
7. **Simulate external tools with their real output.** Copy the actual hook format from a known tool version and record the version in the fixed points. Lefthook's launcher ends with `call_lefthook run "pre-commit" "$@"`. An invented format can make GREEN accept a fake and refuse the real tool. Unknown formats are ambiguities.
8. **A referenced reader needs cases for its known variants** (RULES.md, rule 6). For the TypeScript reader, YAML parser or Shipcraft glob matcher, cover variants a manual implementation might miss: CR, CRLF, U+2028/U+2029, BOM, inline comments, flow style, null, wrong types, wildcards anywhere, quoting and spaces. List the covered variants. An internal trial missed U+2028 and malformed pnpm lists despite naming the correct reader in the spec.
9. **Defect work starts with a main reproduction** (RULES.md, rule 4). Show the command and output before adding other cases. If it does not reproduce, stop and report `needs_input`: the premise may be wrong. Two prior defect premises failed this check.
10. **Cases must not depend on the machine or a fixed version.** Do not create filenames differing only by case: common macOS filesystems treat them as one. Read the expected version from `nucleo/Cargo.toml` or `shipcraft --version`.
11. **Find every case that depends on a changed fixed point.** Search all of `acceptance/` for the affected file, refusal or behavior, and list cases from other items that you adjusted or confirmed. Earlier changes broke 51 cases in one item and five in three others because their shared assumptions were missed.
12. **Run the slice, not the whole battery.** Run `SHIPCRAFT_ACCEPTANCE_CASES` with the item's cases plus every case you adjusted or confirmed under rule 11, the cases the spec's Touches list says change, and, for each "must keep passing unchanged" group of the Touches list (an item, or a named family of cases), one sample module: the cases of one earlier item from that group that exercise the path this item changes. The full Touches list stays the CI contract; CI runs it in the whole battery (2026-10-31, from item 81). For a rename, also search fixtures and sealed locks for old names. The whole battery runs once, in the PR's CI (10 shards, the required `acceptance` check); a local full run repeated it at about 12 minutes a head (item 38 ran it twice). Metric: CI red on a head whose slice was green, at most 1 in 5 items; above that, the local full run comes back. Sample metric: the GREEN's local slice wall time, and CI failures in a "must keep" group the sample did not run; if 2 or more of the next 5 items (81 on) fail in CI on a case the sample should have covered, go back to running every Touches case. Report the slice command, which sample stands for each group, and its `run.sh: total` line.
13. **Read the cases of the items the spec touches, and never contradict them (2026-10-30).** The spec's "Touches" list names the earlier items this one affects, with their case ids. Read those cases and their fixed points before writing any case. A new case must not assert something an earlier case fixes otherwise, unless the spec says the earlier behavior changes. On items 64 to 66 every one of the 5 wrong RED cases contradicted an earlier item: item 54's reuse publishes only the status; item 55 does not lock `__init__.py` and judges each function separately; item 59 names every path outside the globs. Metric: wrong RED cases per item, at most 0.5 over the next 5 items (1.67 on items 64 to 66). Revert: drop this rule and the spec's list.
14. **Read the spec's "Current behavior" list too, and assert what it says to keep (2026-10-30).** The spec lists what today's code does on the paths the item touches: files written, exit codes, messages. For each effect it says keep or change. A case must allow every effect marked keep, even one no earlier case asserts. On item 68 both wrong RED cases forbade a file today's `init` already writes (`locks/.gitkeep` through a symlinked `.shipcraft`), which no item's case pinned. Metric: wrong RED cases per item, at most 0.5 over the next 5 items. Revert: drop this rule and the spec's list.
15. **Fixtures that hold on any machine (2026-10-31).** A fixture never compares clocks across processes (use wall time, `time.time()`, never `time.monotonic()` read in two processes), never depends on the OS (macOS and Linux CI run the same case), never needs the network, and never creates or replaces a path that the hook, `red`, `close` or `init` also write (`.git/shipcraft/runs.jsonl`, `.shipcraft/locks/*`, the closing commit): to block such a path, remove what is already there first, and remember the hook writes a row on every commit. The spec-review brief lists these standing effects. Why: both fixture-caused wrong RED cases of items 69 to 73 broke these rules (item 71 replaced the run log the hook had already written; item 73 compared `time.monotonic()` across processes, which only fails on macOS). Metric: fixture-caused wrong RED cases per item, 2 in 5 today, at most 1 in the next 5 items (from item 74). Revert: drop this rule.
16. **Prove the harness before `red` (2026-11-01).** Every new fixture or shared helper (a fake `gh`, a Go or Node fixture project, a helper that holds expected call lists or reasons) gets one control case that passes on the current binary, through the same helper and the same case routing as the cases that use it. Route each case by its exact id: no `startswith`, `endswith` or shell `pr-*)` arm, so each id matches exactly one arm. A shared helper never holds one case's expected values: it may build the fixture, and each case's own arm sets what that case expects. Before `red`, run `python3 acceptance/tools/routing_check.py acceptance/lib/item<N>.sh` (it lists prefix routing, ids routed twice and helpers that set asserted values, then runs the cases on the current binary through `acceptance/tools/slice.sh` and says, for each failing case, whether the failing assertion is in its own arm, a shared helper or shared code; `--logs <work dir>` reads a slice you already ran), and answer each warning in your report, one line each. Why: 7 of the last 11 wrong RED cases were harness or fixture bugs, not spec readings: item 79's `pr-` prefix block that captured `pr-array-only` and its `missing()` helper that fixed two cases' call lists, item 81's Go fixture, item 76's `invalid-` prefix, item 78's `json-` prefix. Metric: harness or fixture wrong RED cases, at most 1 in total over the next 5 items (from item 83). Revert: drop this rule and the routing check if they are 3 or more.
